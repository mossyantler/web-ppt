> **작성일** — 2026-08-01

## 왜 M2 전에 쓰는가

Z2(라이브 DOM을 직렬화하지 않는다)는 서버 저작 트리를 유일한 진실로 만들었다. 그 대가로 **클라이언트 미러와 서버 트리 사이에 불일치 창**이 생긴다. 커밋이 성공한 뒤 클라이언트를 무엇으로 되맞출 것인가 — 이것이 재조정(reconcile) 문제다.

가장 단순한 답은 "커밋할 때마다 프리뷰를 리로드한다"이고, 이것이 기본값이 되면 M3에서 셋을 잃는다.

1. **선택 상태** — 무엇을 고르고 있었는지가 날아간다.
2. **그룹 진입 스코프** — 컨테이너 안으로 들어가 있던 편집 문맥이 초기화된다.
3. **스크롤 위치** — 긴 덱에서 보고 있던 자리를 잃는다.

그리고 부하 기준(커밋 지연 <150ms)에 **웹폰트 재적용 + KaTeX 재렌더**가 통째로 더해진다. W31 기준 `data-tex` 53곳이 매 커밋마다 다시 그려진다.

이 셋은 M3에서 발견하면 **M3의 설계가 바뀐다.** 그래서 M2 전에 적는다.

## 정책

> **커밋 성공 시 서버 트리의 델타만 클라이언트 미러에 적용한다. 프리뷰 전체 리로드는 문서 스코프 변경에서만 한다.**

### 델타 적용 (기본 경로)

`CommitResult`가 돌아오면 클라이언트는 **자기가 보낸 명령을 근거로** 미러를 갱신한다. 문서를 다시 받지 않는다.

| 명령 종류 | 미러에 적용할 것 |
|---|---|
| 속성 명령 (`setProps`·`setTex`·`setPosition`·`setSectionProps`) | 대상 노드의 속성만 갱신. 자식 서브트리 무변경 |
| 구조 명령 (`insertElement`·`removeElement`·`moveElement`·`duplicateElement`·`wrapElements`·`unwrapElement`) | 해당 슬라이드의 노드 관계만 갱신. `CommitResult.nodeIds` 로 새 id 를 받는다 |
| `setContent` | 대상 리프의 내부만 교체. **리프 밖은 건드리지 않는다** (§6.3 목록 7의 범위와 같다) |

**선택·스코프·스크롤은 보존된다.** 선택은 `data-node-id` 로 다시 찾으며, id 가 안정적이므로 성립한다(§2.2 근거 4).

### 전체 리로드 (예외 경로. 셋뿐이다)

1. **`setTheme`** — 스타일시트 링크가 바뀌어 문서 전체의 조판이 달라진다.
2. **`renumberPages`** — 파생 명령이 문서 전 섹션의 페이지 표시를 건드린다.
3. **외부 편집 유입** — 파일 감시가 외부 변경을 알렸을 때(VS Code 등). 이때는 미러가 근거를 잃었으므로 다시 받는 것 외에 방법이 없다.

이 셋의 공통점은 **문서 스코프**다. 델타를 계산하려면 결국 문서 전체를 봐야 하므로 델타 경로의 이점이 사라진다.

### `superseded` 는 리로드다

`CommitResult.superseded === true` 는 `resultHash ≠ currentHash` 를 뜻한다(§3.3). 미러가 근거로 삼을 상태 자체가 이미 지나갔으므로 **델타를 적용해서는 안 된다.** 문서를 다시 받아 미러를 재구성한다. 이것은 성공이 아니라 **재동기화 신호**다.

## M2 가 지켜야 하는 것

이 정책은 M3 의 구현 지침이지만, **M2 가 만들지 않으면 M3 가 델타를 계산할 수 없는 것**이 있다. M2 의 책임은 셋이다.

- [ ] `CommitResult.nodeIds` 가 **발급된 모든 id** 를 담는다. 구조 명령이 새 노드를 만들었는데 id 가 응답에 없으면 클라이언트는 리로드 외에 방법이 없다.
- [ ] `CommitResult` 가 `resultHash` 와 `currentHash` 를 **항상** 담는다. `applied:false` 인 멱등 응답에서도 마찬가지다 — `superseded` 판정의 근거다.
- [ ] 서버가 커밋마다 **어느 슬라이드가 재직렬화되었는지**를 로그에 남긴다(§11 관측성의 `spliceRanges[]`). 델타 경로가 틀렸을 때 어디를 봐야 하는지가 이 로그에만 있다.

## 검토했으나 기각한 대안

**서버가 델타를 계산해 응답에 담는다** — 기각. 서버가 "무엇이 바뀌었는가"를 트리 구조로 내려보내려면 클라이언트 미러의 이전 상태를 알아야 하고, 그러면 서버가 세션 상태를 갖게 된다. 단일 사용자 로컬 도구에서 그 복잡도를 지불할 이유가 없다. **클라이언트는 자기가 보낸 명령을 알고 있으므로 델타를 스스로 안다.**

**매 커밋마다 문서를 다시 받되 프리뷰만 갱신하지 않는다** — 기각. 네트워크는 로컬이라 싸지만, 미러 재구성 비용과 선택 복원 로직이 델타 적용보다 단순하지 않다. 그리고 `superseded` 경로에서 이미 이 코드가 필요하므로 **둘 다 있는 것이 아니라 예외 경로에만 두는 것**이 맞다.
